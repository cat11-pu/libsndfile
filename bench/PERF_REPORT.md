# PCM 块读取与格式转换优化报告

## 背景

游戏音频资源导入需要把上万条波形统一转码。原实现中，所有需要位深/格式
转换的 PCM 读取路径（`src/pcm.c` 的 `pcm_read_*`）都在栈上使用固定
8 KiB 的 `BUF_UNION` 临时缓冲分块：每次最多读 8 KiB，再逐样本转换到调用方
缓冲。对超大文件和批量导入，这会产生大量 `read()` 系统调用与分块循环。

## 改动概述

- `src/common.h`
  - 新增 `SF_READ_BUFFER_LEN`（64 KiB）。
  - 在 `SF_PRIVATE` 中增加懒分配、随句柄复用的堆缓冲 `readbuf` /
    `readbuf_len`。
- `src/sndfile.c`
  - `psf_close` 中释放 `readbuf`，无泄漏。
- `src/pcm.c`
  - 新增 `pcm_get_readbuf`（懒分配，失败返回 `NULL`）与统一宏
    `PCM_BULK_READ`，替换 28 个需要位宽转换的 `pcm_read_*` 分块函数里重复的
    while 循环；另外 4 个无位宽变化的直读函数（`les2s`/`bes2s`/`lei2i`/
    `bei2i`）保持直接 `psf_fread` 到目标缓冲，不经宏。
  - **阈值策略**：请求量能放进 8 KiB 栈缓冲时仍走原栈路径（行为与原版完全
    一致，避免简单转换在小请求下因堆间接访问变慢）；只有超过栈容量的大块
    传输才使用 64 KiB 堆缓冲。
  - 所有 `*_array` 转换函数原样保留，调用方式不变，因此输出逐位一致。
  - 无位宽变化的直读路径（如本机小端 `pcm_read_lei2i`、`pcm_read_les2s`）
    完全未改动。

## 为什么能提速

大块读取时，单次 I/O 从约 8 KiB 提升到约 36–64 KiB，`read()` 系统调用次数
显著下降。实测对一个 24 bit / 6 声道文件、2048 帧块重复读取：

| 版本 | read() 调用数 | 平均每次读取 |
|------|---------------|--------------|
| 基线（8 KiB 栈） | 8787 | ~7.4 KiB |
| 优化（64 KiB 堆） | 1758 | ~36 KiB |

系统调用数下降约 80%，同时分块循环的判断/回填次数同比例减少。

## 正确性（逐位一致）

- 转换数组函数与归一化系数（`normfact`）一律未改，仅改变承载读取的缓冲。
- 优化前后两个静态库对同一批文件做完整解码，对比 int 与 float 输出的
  FNV-1a 哈希（对全部输出字节、顺序敏感）：
  - 三档基准的 7 个文件 ×（int + float）全部哈希一致。
  - 混合位深/声道的 2000 个文件（4000 条哈希记录）全部一致。
  - 额外边界矩阵：u8/16/24/32 × 声道 1–8 × 奇数帧 × chunk
    1/3/8191/8192/8193/65536 共 525 组全部逐位一致；float 与 double 目标 API
    同样全部一致。
- AddressSanitizer + UndefinedBehaviorSanitizer 构建下，覆盖各格式与大块堆
  缓冲路径，无越界、无未定义行为、无内存泄漏（`readbuf` 在 `psf_close` 释放）。
- 完整测试套件 `ctest`：**144/144 全部通过**，含 `pcm_test`、
  `write_read_test`、`checksum_test`、`floating_point_test`、`pipe_test`、
  `virtual_io_test`、`stdio_test`。

复现方式（分别链接优化库与基线库，对同一份文件）：

```sh
./bulk_read_bench hash file1.wav file2.wav ...   # 对比两个库的输出哈希
```

## 性能（三档文件大小）

测量环境：GCC 15、`-O3 -std=c99`，单核心绑定（`taskset`）降低调度噪声，
每文件重复 50–60 次取中位数。耗时为完整「分块读取 + 格式转换」的墙钟时间。

### 8192 帧块（典型导入块大小）

| 档位 / 规格 | 文件大小 | 基线 (s) | 优化 (s) | 提速 |
|-------------|---------:|---------:|---------:|-----:|
| small / 2ch / 24bit | 0.7 MiB | 0.000216 | 0.000139 | +35.6% |
| medium / 6ch / 24bit | 20.6 MiB | 0.005842 | 0.004741 | +18.8% |
| large / 2ch / 16bit | 54.9 MiB | 0.009697 | 0.007338 | +24.3% |
| large / 8ch / 32bit | 219.7 MiB | 0.021443 | 0.020815 | +2.9% |
| large / 1ch / u8bit | 13.7 MiB | 0.002813 | 0.002187 | +22.3% |

### 32768 帧块（大块批量导入，缓冲优化收益最大）

| 档位 / 规格 | 文件大小 | 基线 (s) | 优化 (s) | 提速 |
|-------------|---------:|---------:|---------:|-----:|
| small / 2ch / 24bit | 0.7 MiB | 0.000220 | 0.000132 | +40.0% |
| medium / 6ch / 24bit | 20.6 MiB | 0.007460 | 0.006397 | +14.2% |
| large / 2ch / 16bit | 54.9 MiB | 0.013304 | 0.009427 | **+29.1%** |
| large / 8ch / 32bit | 219.7 MiB | 0.030935 | 0.030500 | +1.4% |
| large / 1ch / u8bit | 13.7 MiB | 0.003223 | 0.002756 | +14.5% |

说明：
- 转换路径（8/16/24 bit → int/float，需要临时缓冲加宽）收益最明显，
  大块下 16 bit 稳定达到约 30%，24 bit 多声道约 12–17%。
- 32 bit 本机小端走「直读 + 可选 endswap」路径，不经临时缓冲，本就没有
  分块瓶颈，因此基本持平（差异在测量噪声 ±5% 内），且无回退。
- 8 bit 等极简转换在小请求下通过阈值保留原栈路径，避免了早期「一律用堆」
  方案观察到的约 8% 回退；大块时仍有 +13% 以上收益。

## 边界覆盖

- 超长文件：`large_*` 档单文件最长 1440 万帧（54–220 MiB 数据）。
- 多声道：覆盖 1、2、6、8 声道。
- 不同位深：u8、s16、s24（tribyte）、s32，以及 int/float 两种目标类型。
- 小请求与大请求、文件尾部不足一块的 partial read 均由现有
  `readcount < bufferlen` 分支处理，行为与原版一致。

## 备选但未采纳的方向

- 手写 SSSE3 `pshufb` 加速 24 bit 三字节解包：原型验证收益不稳定（0–11%），
  且引入平台 intrinsic 与复杂的 lane 边界处理，损害可移植性与可维护性，
  与「逐位一致、稳健」目标不符，故未采纳。
